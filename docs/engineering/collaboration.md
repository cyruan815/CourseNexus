# Collaboration v0.1

## 团队分工

当前协作模型面向小团队：

- 项目负责人 / 架构师：维护 PRD 口径、架构基线、模块边界、数据模型方向和跨端契约。
- 后端开发 2 人：实现 FastAPI 后端、数据模型、鉴权、资料解析、Agent 编排、计划任务和状态一致性。
- 前端开发 1 人：实现 React 前端、页面路由、交互状态、表单、日历、任务执行和错误 / 空状态。

## 分支策略

- `main` 是稳定分支，只接收经过验证的发布版本和必要的紧急修复。
- `dev` 是日常开发集成分支，所有新功能以最新 `dev` 为基线。
- 每项工作使用独立短期分支，建议命名为 `feature/<short-name>`、`fix/<short-name>`、`docs/<short-name>` 或 `chore/<short-name>`。
- 开发者不得直接向 `main` 或 `dev` 推送；普通功能、修复和文档改动通过 PR 合并到 `dev`。
- 功能分支在 PR 合并后删除，不长期保留个人或固定开发分支。
- `dev` 达到发布标准后，由项目负责人发起 `dev` 到 `main` 的发布 PR；发布合并后及时让 `dev` 与 `main` 重新同步。
- 紧急修复从 `main` 创建 `hotfix/<short-name>`，PR 到 `main`；合并后必须把同一修复同步回 `dev`。
- 一个分支只承载一项可独立评审的工作，各可验证小改动仍按独立 commit 提交。

### 日常开发循环

1. 开发者更新本地 `dev`，再创建短期工作分支：

```bash
git fetch origin
git switch dev
git pull --rebase origin dev
git switch -c feature/<short-name>
```

2. 开发者完成代码、测试和领域文档，按可验证的小改动分别 commit，经明确授权后推送该工作分支。
3. 开发者从工作分支向 `dev` 提交 PR；PR 描述必须包含变更目的、影响范围、最新 commit、测试命令与结果、文档更新和已知问题。
4. 项目负责人审查 PR，重点检查业务验收、代码缺陷、权限与状态流转、测试结果、领域文档、API/数据契约和模块边界。
5. 发现问题时，开发者继续向原工作分支提交修复；需要同步最新 `dev` 时使用 rebase，并重新运行受影响测试。
6. PR 通过后合并到 `dev`，随后删除远程和本地工作分支。
7. `dev` 达到稳定发布标准后，项目负责人创建 `dev` 到 `main` 的发布 PR。发布后更新本地 `main`、同步 `dev`，并确认两条长期分支不存在意外分叉。
8. `git push --force-with-lease` 只允许用于开发者自己的短期工作分支，且只能在明确授权下用于 rebase 后更新；不得强推 `main`、`dev` 或其他人的分支。

## Commit 规范

提交信息使用 Angular / Conventional Commits 结构：

```text
<type>(<scope>): <subject>

<body>

<footer>
```

`subject` 是必填的首行摘要，位于冒号之后，须简明扼要（不超过 50 个字符），并以动词开头。

`body` 是可选正文，与首行之间空一行。出现以下情况时应补充 `body`：

- 改动原因或问题根因无法从 `subject` 直接看出。
- 存在关键实现约束、取舍或容易误解的非显然行为。
- 涉及兼容性、数据迁移、配置变化、回滚要求或后续操作。
- 一个原子提交包含多处必要的协同修改，需要说明它们为何必须一起提交。

简单且自解释的改动不需要 `body`。正文重点解释“为什么改”和评审者必须知道的影响，不重复罗列文件名或逐行复述代码。

`footer` 是可选尾注，与 `body` 之间空一行，适用于：

- 使用 `BREAKING CHANGE:` 说明破坏性变更及迁移要求。
- 使用 `DEPRECATED:` 说明弃用内容和推荐替代路径。
- 使用 `Fixes #...`、`Closes #...`、`Refs #...` 关联或关闭 Issue / PR。

规则：

- `type` 使用英文固定标识，例如 `feat`、`fix`、`docs`、`test`、`refactor`、`chore`、`build`、`ci`、`perf`、`style`、`revert`。
- `scope` 可选，使用英文短名标识影响范围。
- 除模板字段和固定标识外，`subject`、`body` 和说明性内容使用中文。
- 文档类提交使用 `docs`，不要使用非 Angular 规范的 `doc`。

示例：

- `docs(engineering): 明确提交信息使用中文说明`
- `feat(courses): 新增课程列表骨架`
- `fix(api): 修正未登录错误响应`
- `test(tasks): 覆盖任务完成状态流转`

需要正文时：

```text
fix(materials): 避免部分解析静默标记成功

Docling 可能在部分页面失败后仍返回非空文档。记录解析诊断，供下游区分完整解析和部分解析。
```

需要尾注时：

```text
feat(api): 区分资料可用状态和解析质量

保留 parsed 作为可消费状态，并单独暴露解析质量，避免部分成功资料被下游完全排除。

BREAKING CHANGE: material 响应新增 parse_quality 字段
Refs #123
```

一次提交只做一类事情，避免混入无关格式化或临时文件。

提交粒度按“小功能 / 小修复 / 小文档规范变更”切分：

- 每完成一个可验证的小功能或小改动，就提交一次。
- 不等完整大功能全部做完再统一提交。
- 同一个小改动需要的代码、测试和文档应放在同一次提交中。
- 不把多个业务模块、多个页面流程或多个无关规范调整混进同一次提交。
- Agent 执行任务时也遵守同一粒度；除非开发者明确要求暂不提交，否则完成小改动并验证后可以自动 commit。
- 涉及视觉、布局、交互手感或用户截图反馈的前端改动，Agent 必须先完成小范围修改并向开发者说明改动点和待查看位置，等待开发者确认视觉方向后，再运行完整验证并 commit；不得在开发者看到效果前先测试、提交或把可能错误的视觉方案固化进历史。
- Agent commit 前必须检查 `git status`、`git diff` / `git diff --staged`、待提交文件范围、是否包含敏感文件或密钥、以及本次验证命令结果；发现无关改动、真实 `.env`、密钥、用户资料正文或未解释的测试失败时不得提交。
- `git push`、`git push --force-with-lease`、创建 PR 和合并 PR 属于远程仓库操作，Agent 只有在开发者明确下达指令后才能执行；不得因为本地 commit 已完成就自动 push 或自动创建 PR。

## PR / Review 规则

- 开发者负责创建 PR，但不得自行批准、合并 PR 或直接推送 `main`、`dev`。
- PR 描述必须说明变更目的、影响范围、最新 commit、测试命令与结果、文档更新和已知问题。
- PR 未合并前，对应工作分支只追加该 PR 的 Review 修复。新任务必须从最新 `dev` 创建另一条短期分支。
- 项目负责人负责审查 PR，必须检查业务验收、代码缺陷、权限与状态流转、测试结果、领域文档、API/数据契约、文件所有权和禁止事项，不能只依据“测试通过”批准。
- Agent 可协助拉取、检查和本地验证 PR，但必须先完整报告审查结论；提交 review、评论、批准、请求修改、关闭或撤回 review / comment 前，必须获得开发者对该具体远程操作的明确确认。仅“审查 PR”不构成远程写操作授权。
- 普通模块内部改动通过审查后合并到 `dev`；只有达到发布标准的 `dev` 才通过发布 PR 进入 `main`。
- 涉及数据库、migration、公共 API、共享 schema、架构边界、核心依赖或跨开发者共享文件的变更，开发者必须在 PR 中提交风险摘要，由项目负责人确认后才能合并。
- 发现阻断问题时不得批准或合并；项目负责人应给出文件和行号级问题清单，开发者修复并更新原 PR 后重新审查。
- 涉及 API、字段、状态、模块边界、工程约定的变更，必须先更新对应 `docs/`。
- Review 优先关注数据归属、状态流转、错误处理、契约一致性和测试覆盖。
- 小修小补可以轻量 Review；跨模块或数据模型变化必须由项目负责人 / 架构师确认。

## 任务拆分原则

- 先拆 walking skeleton，再拆完整业务功能。
- 后端任务按数据对象、服务边界和 API 契约拆分。
- 前端任务按页面、流程和可复用组件拆分。
- Agent 相关任务必须明确输入、资料范围、输出、引用来源、失败状态和保存对象。
- 任务不应跨越多个模块内部实现，除非它本身是明确的集成任务。

## 模块负责人职责

- 确认模块边界与 [../architecture/module-boundaries.md](../architecture/module-boundaries.md) 一致。
- 维护模块涉及的 API、字段、状态和验收口径。
- 维护 [../domains/index.md](../domains/index.md) 中本领域的实际实现文档，确保代码入口、架构、状态、算法和测试证据与当前提交一致。
- 发现 PRD、架构、契约不一致时，先更新文档或提请确认。
- 不把临时实现细节写成长期规则。

## 领域文档交付门槛

- 每个功能任务开始时必须在 Issue、任务描述或 PR 描述中声明唯一的 `docs/domains/<domain>/...` 写入路径。
- 代码实现、测试和领域文档同步推进；不得在功能合并后再由其他人补写实现说明。
- 前端领域文档必须记录页面/组件边界、交互状态、API 数据流、异常降级和手工验收入口。
- 后端领域文档必须记录组件架构、实际代码地图、数据流、核心算法、事务/幂等/补偿、复杂度或资源预算及测试入口。
- AI 后端还必须记录 prompt 职责、结构化 schema、map/reduce、材料覆盖、去重和引用约束。
- Review 必须把领域文档与代码逐项核对；缺少、过期或只描述目标而不描述实际实现时，任务不得验收。
- 领域文档引用全局 PRD、架构和 API 契约，不复制并形成第二套权威字段表。

## 冲突处理方式

- PRD 与实现冲突时，以 [../product/prd.md](../product/prd.md) 为产品入口，必要时由项目负责人确认。
- 架构与实现冲突时，先更新 ADR 或模块边界，再改代码。
- API / 数据契约冲突时，先更新 [../api-data/index.md](../api-data/index.md)。
- 文档之间出现矛盾时，以更具体分区为准，并同步修正入口文档。

## 文档更新责任

谁修改长期行为，谁负责更新文档。Agent 参与任务时，也必须把产品、架构、API、数据契约和工程规范变化沉淀到 `docs/`，并把功能的实际实现沉淀到 `docs/domains/`，不能只写在回复或代码注释中。
